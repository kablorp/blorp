# Blorp 2 attribution after O1

Measured 2026-10-30 at `ae4710afc` (seed `blorp2-seed-9df029bac05b`; the scripts added with this report are the only
other change) on an Apple M4, Apple clang 21.0.0, macOS 26.7.1, for the
["Attribution after O1"](../../blorp_2/ROADMAP.md#attribution-after-o1) step. It changes no production code.

```sh
blorp_2/scripts/attribution/run          # 3 min 59 s at load 2.5 to 3.7; 5 to 9 minutes under heavier load
```

The raw samples, instrumented C and tables are written to `build/blorp_2_attribution/`, which git ignores. They exist
only there, are not committed, and are regenerated by the command above. Counts are exact and repeat between runs;
the profile and the timing depend on the machine.

## What this decides

- **Projection acquisitions (borrowed field projections).** Projection acquisitions and the drops of their owners
  are 239.3 M of the 733.5 M atomic operations (32.6%): 29.4% of record operations, 51.4% of List, 34.0% of String,
  5.9% of boxed union. The five functions with the most hold 64.1% of the 120.5 M acquisitions; the specialization
  lookups alone are 45.9 M, and module `specialize` is 32.2% of all operations. An escaping projection is moved, not
  dropped, so this pool is an upper bound for borrowing; whether the parent outlives each use was not checked.
- **Cascades and rebuilds (O3).** Cascades are 33.9 M operations (4.6%). Record work a reused cell could skip,
  record decrements in cascades plus record increments for stored fields, is 32.5 M of 320.7 M record operations
  (10.1%); that is neither an upper nor a lower bound (cascades also free other parents' records; the old cell's
  own drop is not included). Which of the 9.95 M record allocations (51.7% of allocations) rebuild a dying cell was
  not measured.
- **Acquire-then-drop at stores and control edges.** Significant: 138.1 M operations (18.8%) are acquisitions from
  an owner that is dropped right after in the same operation list, so a move would replace both. 92.8 M (12.6%) are at
  the end of a block, mostly Lists (75.1 M), and 45.3 M (6.2%) are at stores. Pairs spanning two operation lists
  are not seen, so this is a lower bound.
- **Remaining copy work.** 38.5 M List slots (2.0 M calls) and 213.6 MB of String; 109.7 MB of the String bytes
  come from one site, `append_owner_alias`, and 43.8 MB from `list.join_range`. The list helpers append, concat and
  set perform 20.2 M RC operations (2.8%).
- **Saving from removing atomicity.** Plain counts at a fixed operation count used 7.5% fewer cycles (best of five;
  5.9% to 8.5% per pair, median 8.2%) on this M4. It is an estimate for this machine, not an upper bound: the plain
  build retires 2.9% more instructions and keeps every operation.

## 1. Copies

The method is O0's: every in-place helper (`*_take_left`) and borrowed update helper counts its calls and the List
slots or String bytes it moves, by return address, symbolized to a Blorp function and a statement of
`statements.c` (the generated C with one statement per line). The `/* module.function */` comments replace O0's name
map. The program is built with `-fno-optimize-sibling-calls`: a function that returns a helper's result by a tail
call is otherwise missing from the stack, and its copy is charged to its caller (the `emit` row below).

**`append_owner_alias` (unchanged).** Its `output` is an owned parameter now: 55,510 of its 71,215 calls update a
unique String in place. The other 15,705 arrive shared and copy about 7 KB each. Their callers, `append_input_owners`
(8,030 String acquisitions for an owned parameter), `append_join` (6,401) and `append_loop` (1,322), still use
`output` after the call, so the call acquires (`blorp_string_retain` in their C) instead of moving. In
`append_input_owners` the shape is

```blorp
var result = output
for input in inputs:
    ...
    match append_owner_alias(result, owner, ...):
        Ok(aliased): result = aliased
        Err(error):
            failure = Some(error)
            break
match failure:
    Some(error): Err(error)
    None: Ok(result)
```

`result` is live on the `break` edge whatever `failure` says, so the call is not its last use. The 16,425 fallbacks
of `append_selection_body` are the same pattern: `append_selection` acquires its String `output` 16,425 times
before the owned call.

**`with_bucket_entry` (reduced).** O0's 65.6 M slots were the outer `buckets.set(bucket, ...)` copying the bucket
table on every call. It is in place on 13,593 of 13,645 calls now; 52 calls copy 245,740 slots (cause not traced).
The inner `listed.append(id)` falls back on all 13,645 calls, as the roadmap says, copying 5,897 slots in all: in
the generated C, `listed` comes from `list.get`, whose `Some` payload holds a second reference to the bucket
(`blorp_list_dup_0_i`) while the `buckets` table holds the first.

**`emit` (closed by O1).** The three `output.concat(...)` calls in the `WithArguments` arm of `emit` were real
23 MB copies of a borrowed String: O0's `text.concat` took `left` borrowed and appended with a copying
`StringConcat`. The tail call hid the helper, so O0 charged the copies to `emit`, the correct call site. O1 inferred
`left` owned: in the current C `text.concat` aliases `blorp_p_0` as an owner and calls
`blorp_string_concat_take_left` on it, its 21,901 fallbacks copy 333,782 bytes in all, and `emit` itself calls
`blorp_string_concat_take_left` at two sites that run once each, in place, on 24.5 MB (statements.c lines 101326
and 101344).

## 2. Atomic reference-count operations

Every `atomic_fetch_add_explicit` and `atomic_fetch_sub_explicit` in the self C is counted (1,650 sites, all inside
function bodies; the diagnostic-only shared-empty-List counter is a macro without an atomic in the normal build, as in
O0). The kind-only build is O0's method. The tagged build adds the source:

- **Markers.** A scratch patch of `emit` writes a comment around each `AcquireOwner` and `DropOwner` and after each
  owner that a definition, a join output, a loop header or a loop or arm input creates. It reads ownership's
  operations where emit already walks them. An acquisition's reason comes from its neighbours, on the assumption that
  ownership inserts it directly before the operation it serves: `projection` if the previous operation is the
  `ReadRecordFieldDefinition` it acquires, `call` or `stored` if the next definition is a call or a construction or
  capture, `block_end` if no operation follows (`before_control`, for a join or loop next, never occurs). A drop is
  tagged with the origin of its owner; the run fails if no marker created that owner.
- **Tagging.** Every dup or drop helper call becomes `(tag = T, helper)(...)`. A drop helper's calls after its own
  decrement are `cascade`; list helpers' calls are `runtime_list`; helpers with no atomic of their own run under their
  caller's tag. The tag also carries the Blorp function number.
- **Proof.** Tagged counts sum to the kind-only counts for every kind and direction, none is unattributed, every
  drop has an origin, and both counting compilers write the self C. The marker compiler's output with markers
  stripped is byte-identical to B's.

## 5. Saving from removing atomicity at a fixed operation count

A copy of the self C in which every atomic add and sub is a relaxed load and store (orders dropped), so every
operation is kept and only atomicity goes. The compiler is single-threaded, so this is valid for this measurement
only. The atomic build has 78,221 `ldadd`/`ldaddal` instructions and the plain build none (the driver fails
otherwise). Both write the self C. Five samples each, serial, alternating which build goes first; cycles are
`/usr/bin/time -l`'s "cycles elapsed".

**Best of 5**

| Build | Seconds | Cycles | Instructions retired |
| --- | ---: | ---: | ---: |
| atomic | 1.300 | 5,217,339,113 | 20,736,796,382 |
| plain | 1.200 | 4,823,476,841 | 21,333,326,909 |

Plain over atomic, best of each: 7.7% less time, 7.5% fewer cycles, 2.9% more instructions.

Per pair (same sample number), the plain build used 5.9% to 8.5% fewer cycles, median 8.2%.


The plain build retires 2.9% more instructions: a load, an add and a store replace one `ldadd`. This is an M4 with
LSE atomics, where an uncontended `ldadd` is cheap; other cores, or x86's `lock xadd`, were not measured. The range rests on this one retained run.

## Not measured, and limits

- Pairs that span two operation lists are not move candidates here.
- Projection pairs assume the projection could have been borrowed; whether its parent stays alive was not checked.
- Which record allocations rebuild a unique cell was not measured.
- One profile sample; five timing pairs.
- A counted operation's data kind comes from the helper function's name (`blorp_record_*`, `blorp_list_*`,
  `blorp_union_*`, `blorp_string_*`), as in O0; `emit` generates these names.
- `sample` runs concurrently with the profiled program, the driver's one concurrency; no two measured programs run
  together.
