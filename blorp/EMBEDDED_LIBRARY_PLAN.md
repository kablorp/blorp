# Embedding the standard library in `blorp`

Status: approved by Keith on 2026-11-07 (revision 3, after review), with E1
decided as (b), generated on every build, and E2 as `<standard library>/...`.
This is the design note that `CLI_PLAN.md` (P2) requires before code.

## Problem

`blorp compile` needs `--library-root` to find the standard library, so a
user must know where `blorp/standard_library` lives:

```sh
$ blorp compile hello.brp
blorp: error: blorp compile needs --library-root
```

Keith decided on 2026-11-07 (CLI plan, Decision 2) that the library is
embedded in the binary, "what we did with the legacy compiler", with
`--library-root` kept as an override. After this change `blorp compile
hello.brp` works from any directory.

## Background

- **Legacy precedent** (`git show a52cf7d44^:Makefile`, ~58-160): the seed
  built a Blorp generator that wrote an untracked
  `blorp/src/compiler/stage_01_generated_inputs/embedded_std.brp` on every
  build, and the frontend consulted `embedded_std_contains_module`.
- **Load today** (`blorp/src/compile/load/load.brp`): `library_layout`
  (`:74`) builds an opaque `LibraryLayout` from the root path; `module_role`
  (`:87`) classifies a path as foundation types, foundation prelude, library
  or user module, and the role, fixed when a module is queued, is its only
  role authority; `read_module` (`:169`) reads every module with
  `fs.read_text`.
- **The library** is 17 `.brp` files, about 64 KB, in
  `blorp/standard_library/`.
- **Cost of literals**: String literal bytes are static C arrays
  (`emit.brp:313-340`), a String is built on first evaluation
  (`runtime/string.brp:138-162`), and a String-pattern arm is a length and
  `memcmp` test (`emit.brp:2703-2712`). `src/compile/runtime/` already holds
  about 154 KB of literals.
- **Ceilings** (`CLI_PLAN.md`): binary within +256 KB of P1's; self-compile
  allocations and retired instructions each within +1%; `make -C blorp
  compiler` wall time within +10%.

## Proposed solution

### The embedded module

One module holds every library file's text, behind one lookup:

```blorp
-- Generated from blorp/standard_library by blorp/scripts/embed_library.brp
-- during `make -C blorp compiler`. Do not edit; it is rewritten when the
-- library changes.

-- The text of the library file at `path`, relative to the library root.
pure func embedded_library_file(path: String) -> Option[String]:
    match path:
        "_base.brp":
            Some(
                "-- The configured foundation...\n...",
            )
        ...
        _:
            None


-- Every embedded file's path, in byte order.
EMBEDDED_LIBRARY_PATHS: List[String] = ["_base.brp", "bool.brp", ...]
```

The generator escapes `\`, `"` and `${` (as `$\{`), LF as `\n`, tab as
`\t`, CR as `\r`, NUL as `\0`, and every other control byte and DEL with the
lexer's escape form (or rejects the file naming the byte, if the lexer has no
escape for it; the library has none today), and writes all other bytes as is.

### E1: how the module is produced (decided: generated on every build)

Keith chose (b), the legacy approach, on 2026-11-07. The module is not
tracked: Make writes it to `blorp/build/generated/embedded_library.brp`
(ignored with the rest of `blorp/build`), and Load imports it as
`../../../build/generated/embedded_library`, with a comment at the import
saying why it leaves `src/`. Relative imports out of `src/` have precedent in
the test suites, and the layer test constrains only `syntax/` and `format/`.

The rejected alternative was a committed file regenerated by hand: no build
machinery, but every library change would appear twice in a diff.

### Build

The generated file is a real Make file target, so it is rebuilt only when
the library or the generator changes:

```make
# blorp/Makefile; Make runs in blorp/, so paths are relative to it.
EMBED_LIBRARY := build/generated/embed_library
EMBEDDED_LIBRARY := build/generated/embedded_library.brp

$(EMBED_LIBRARY): scripts/embed_library.brp      # built by the pinned seed
$(EMBEDDED_LIBRARY): $(EMBED_LIBRARY) $(wildcard standard_library/*.brp)
generate-compiler test-compiler: $(EMBEDDED_LIBRARY)
```

- The pinned seed compiles the generator with its old interface
  (`--library-root blorp/standard_library scripts/embed_library.brp OUT.c`),
  `BLORP_CC` links it, and the file target runs it. Everything it uses
  (`fs.list_directory`, `read_text`, `write_text`, String patterns) is in the
  pinned seed.
- `scripts/blorp-fixpoint` needs no change: stage A builds through
  `test-compiler`, which depends on the file, and B and C reuse the same tree.
- `.github/workflows/blorp-seed.yml`: run `make -C blorp
  build/generated/embedded_library.brp` before the reference-A step (`:79`).
- `blorp/test/tooling/test_bootstrap.sh`: its recipe test (`:273-278`)
  asserts exactly one seed call and the `seed,link:0,link:1` cc log; it must
  expect the generator's seed call, link and run, and its fixture repository
  needs a stub `scripts/embed_library.brp` and `standard_library/` so the fake
  cc produces a runnable stub. Plan this change with the test, not after.
- Benchmark recipes and anyone who runs a compiler directly on
  `src/main.brp` must build the file first; `blorp/AGENTS.md`, `README.md` and
  `benchmarks/README.md` say so (`make -C blorp compiler` does it).
- **`blorp format` and `blorp/build`.** The generated file is not formatted
  (its arms hold long literals). The repository's formatting gate names its
  roots (`blorp/scripts blorp/src blorp/standard_library blorp/test`), so it never walks
  `blorp/build`; the README and AGENTS.md tell contributors to format the
  files they changed or to run the gate's command, not `blorp format blorp`.

### The generator

`blorp/scripts/embed_library.brp` (beside the repository's other build
scripts), `embed_library LIBRARY_ROOT OUTPUT`: lists the library root
(sorted, `.brp` files only; a subdirectory is an error until the library has
one), reads each file, and writes the module directly (Make's file target
handles staleness, so no compare-and-rename step is needed). A pure
`render_embedded_library(files: List[(String, String)]) -> String` does all the
text work, so it is unit-tested without the file system.

### Load

The layout records where library modules come from, so the source and the
paths cannot disagree:

```blorp
union LibraryLayout:
    -- Library and foundation modules under a directory.
    LibraryDirectory(LibraryContents)
    -- The embedded copy; its modules get paths under EMBEDDED_LIBRARY_ROOT.
    EmbeddedLibrary


-- The root of embedded library paths in diagnostics. A relative name in angle
-- brackets cannot equal a path Load builds, which are absolute.
private EMBEDDED_LIBRARY_ROOT: String = "<standard library>"
```

As built, Load has two unions, because two unions in one module cannot share
constructor names. `LibrarySource` (below) is the command line's choice and keeps
the names `EmbeddedLibrary | LibraryDirectory(String)`. `LibraryLayout` is opaque
over a private union named after what differs, `ReadFromDirectory(LibraryContents)
| ReadFromEmbedded`; the embedded variant holds nothing, and its paths derive
from `EMBEDDED_LIBRARY_ROOT`, so they cannot disagree with it.

- `CompileRequest.library_root: String` (P1) becomes `library:
  LibrarySource` (`EmbeddedLibrary | LibraryDirectory(String)`); `--library-root
  DIR` gives the directory, no flag gives the embedded copy.
- `module_role` works on either layout; for `EmbeddedLibrary` the prefix is
  `EMBEDDED_LIBRARY_ROOT/`.
- Reading dispatches on the module's role and the layout, not on a path
  prefix: a library or foundation module under `EmbeddedLibrary` is read with
  `embedded_library_file`; every other module with `fs.read_text`. A library
  path with no embedded file is today's missing-import diagnostic.

### E2: embedded library paths in diagnostics (decided)

Keith chose `<standard library>/list.brp` on 2026-11-07: it cannot collide
with a user path, which Load always makes absolute, and tells the reader the
file is built in.

## Scope and non-goals

In scope: the generator, the Make file targets, Load's layout,
`CompileRequest`, the seed workflow step, `test_bootstrap.sh`, and every test and
text that says `--library-root` is required:
`blorp/test/e2e/self_hosted_cli.brp:69-78, 216, 290, 294-305`;
`blorp/src/compile/load/load.brp:192, 479, 516` ("read from
--library-root"); `blorp/src/cli.brp:78-87, 292, 325-328`; `blorp/AGENTS.md`
(`:100-110`), `README.md`, `benchmarks/README.md`, `scripts/README.md`,
`CLI_PLAN.md` (P2 status).
Not in scope: `blorp test`/`blorp run` (P3); embedding the C runtime (already
in the emitted C); library subdirectories; seed rotation (no builtin is
added). Tests and the driver keep passing `--library-root
blorp/standard_library`: they test the library on disk.

## Risks and unknowns

- **Literal cost**: about 64 KB of literals, roughly 250 KB of C text. Measure
  the ceilings; over one, stop and report.
- **Build order.** A compile of `src/main.brp` without the generated file
  fails with "could not read module …/build/generated/embedded_library.brp";
  the docs state the build-first rule, and the import's comment names
  `make -C blorp compiler`.
- **Wall time.** Building the generator with the seed adds to `make -C blorp
  compiler`; measure it against the +10% ceiling (a rebuild with an unchanged
  library skips it).
- **A diagnostic inside embedded library code** has no easy trigger (the
  library compiles); test the path spelling through a unit test of Load's
  layout instead of an end-to-end diagnostic.

## Testing

- **Generator** (unit): `render_embedded_library` on small inputs covering
  every escape, a CR, a NUL and another control byte; the output parses, and
  each arm's literal decodes to its input byte for byte.
- **Freshness** (component suite; it imports the generated module, which
  `test-compiler` builds first): `EMBEDDED_LIBRARY_PATHS` equals the sorted
  `.brp` listing of `blorp/standard_library`, and `embedded_library_file`
  returns each file's exact text. Red check: change the library in a scratch
  copy of the generated module and confirm the test names the file.
- **CLI** (e2e): `blorp compile <absolute temp path>/hello.brp -o …` with no
  `--library-root` writes C byte-identical to the same compile with
  `--library-root blorp/standard_library`; `--library-root` pointing at a copy
  whose `list.brp` was changed uses the change.
- **Load** (unit): `module_role` and path display under `EmbeddedLibrary`.
- Gates: `make -C blorp test`, then `make -C blorp test-e2e
  INSTRUCTION_CHECK=on`, `bash blorp/test/tooling/test_bootstrap.sh`,
  `scripts/blorp-fixpoint --prove`; the ceilings against P1's compiler.

## Acceptance criteria

- From `blorp/`, `../bin/blorp compile src/main.brp -o main.c` (no flag)
  writes C byte-identical to `--library-root standard_library`.
- After editing a library file, `make -C blorp compiler` regenerates the
  module and the freshness test passes; a hand-edited stale module fails it.
- All ceilings hold, reported with production and test line counts; all
  gates pass.

## Release strategy

One landing. Back out by reverting it; `--library-root` keeps working
throughout.
